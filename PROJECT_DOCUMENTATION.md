## Общая архитектура проекта

### Концепция приложения
**Habits Telegram Mini App** - это полнофункциональное приложение для отслеживания привычек, которое работает внутри Telegram клиента как WebApp. Приложение позволяет пользователям создавать задачи/привычки, отслеживать их выполнение, вести статистику и делать записи в дневнике.

### Архитектурный подход
Проект использует **трехзвенную архитектуру**:
1. **Frontend** - React приложение с современным UI (Vite, TailwindCSS)
2. **Backend** - REST API на FastAPI (Python)
3. **Database** - SQLite (локально) / PostgreSQL (production)

### Интеграция с Telegram
- Аутентификация через Telegram WebApp API (`X-Telegram-Init-Data` header)
- Работа внутри Telegram WebView
- Telegram бот для запуска приложения

## Backend - Обзор

### Технологический стек
- **FastAPI** - современный веб-фреймворк для Python
- **SQLAlchemy** - ORM для работы с БД
- **Pydantic** - валидация данных
- **python-telegram-bot** - аутентификация Telegram

### Основные компоненты

#### 1. Точка входа (`main.py`)
FastAPI приложение, которое:
- Настраивает CORS для работы с фронтендом
- Определяет все API endpoints
- Обрабатывает аутентификацию пользователей
- Запускает инициализацию БД при старте

#### 2. Модели данных (`models.py`)
SQLAlchemy модели:
- `Task` - основная модель задачи/привычки
- `Subtask` - подзадачи для задач
- `Note` - записи в дневнике

#### 3. Бизнес-логика (`crud.py`)
Содержит всю логику работы с данными:
- CRUD операции для задач и подзадач
- Автоматическое обновление статусов задач
- Вычисление стриков (последовательных выполнений)
- Фильтрация задач по датам и частоте

#### 4. Аутентификация (`telegram_auth.py`)
Валидация данных Telegram WebApp:
- Проверка подписи данных через HMAC-SHA256
- Извлечение user_id из initData
- Проверка срока действия данных

## Backend - Детальное описание файлов

### `backend/app/main.py`

#### Логика работы:
**Назначение**: Точка входа FastAPI приложения, определяет все API endpoints и middleware.

#### Основные компоненты:

1. **Инициализация приложения**:
   ```python
   app = FastAPI(title="Habits Mini App API")
   ```
   - Создает экземпляр FastAPI приложения

2. **CORS Middleware**:
   ```python
   app.add_middleware(CORSMiddleware, ...)
   ```
   - Разрешает запросы с любых источников (для разработки)
   - В production должен быть настроен список разрешенных доменов

3. **Инициализация БД при старте**:
   ```python
   @app.on_event("startup")
   def on_startup():
       init_db()
   ```
   - При запуске создает таблицы и применяет миграции

4. **Аутентификация пользователя**:
   ```python
   def get_user_id(x_telegram_init_data: str | None = Header(...)):
   ```
   - Извлекает `X-Telegram-Init-Data` из заголовков запроса
   - Валидирует данные через `telegram_auth.py`
   - Возвращает `user_id` для дальнейшего использования
   - В DEV режиме может использовать `DEV_USER_ID` из переменных окружения

#### API Endpoints:

**Health Check endpoints**:
- `GET /health` - базовая проверка работоспособности
- `GET /health/db` - проверка подключения к БД
- `GET /health/full` - полная диагностика (версия Python, переменные окружения)

**Tasks endpoints**:
- `POST /task` - создание новой задачи
- `PUT /task/{task_id}` - обновление задачи
- `DELETE /task/{task_id}` - мягкое удаление задачи (архивирование)
- `GET /tasks?date=YYYY-MM-DD` - получение списка задач для выбранной даты
- `POST /task/{task_id}/complete` - переключение статуса выполнения задачи

**Subtasks endpoints**:
- `POST /subtask` - создание подзадачи
- `PUT /subtask/{subtask_id}` - обновление подзадачи
- `DELETE /subtask/{subtask_id}` - удаление подзадачи
- `POST /subtask/{subtask_id}/complete` - переключение статуса подзадачи

**Statistics endpoints**:
- `GET /stats?period={day|week|month|all}` - статистика по периодам
- `GET /habits` - статистика по категориям привычек

**Notes endpoints**:
- `POST /notes` - создание записи в дневнике
- `GET /notes?date=YYYY-MM-DD` - получение записей за дату
- `DELETE /notes/{note_id}` - удаление записи

**Migration endpoint**:
- `POST /migrate` - ручной запуск миграций БД

#### Реализация:
- Все endpoints используют dependency injection для получения `db` (сессии БД) и `user_id`
- Обработка ошибок через HTTPException
- Логирование всех операций через `logger`

### `backend/app/database.py`

#### Логика работы:
**Назначение**: Настройка подключения к базе данных и управление сессиями.

#### Основные компоненты:

1. **Определение DATABASE_URL**:
   ```python
   DATABASE_URL = os.getenv("DATABASE_URL")
   if not DATABASE_URL:
       # Дефолтный путь для SQLite
       DATABASE_URL = f"sqlite:///{db_path}"
   ```
   - Использует переменную окружения или путь по умолчанию
   - Поддерживает SQLite (локально) и PostgreSQL (production)

2. **Исправление PostgreSQL URL**:
   ```python
   if DATABASE_URL.startswith("postgres://"):
       DATABASE_URL = DATABASE_URL.replace("postgres://", "postgresql://", 1)
   ```
   - SQLAlchemy требует `postgresql://` вместо `postgres://`

3. **Создание engine**:
   ```python
   engine = create_engine(DATABASE_URL, ...)
   ```
   - Создает connection pool для БД
   - Для SQLite отключает проверку потоков (`check_same_thread=False`)

4. **SessionLocal**:
   ```python
   SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)
   ```
   - Фабрика для создания сессий БД

5. **Base для моделей**:
   ```python
   Base = declarative_base()
   ```
   - Базовый класс для всех SQLAlchemy моделей

#### Функции:

**`init_db()`**:
- Импортирует модели (чтобы они зарегистрировались в Base.metadata)
- Создает все таблицы через `Base.metadata.create_all()`
- Применяет миграции через `migrations.migrate_all()`
- Вызывается при старте приложения

**`get_db()`**:
- Dependency для FastAPI
- Создает сессию БД
- Выполняет тестовый запрос для проверки подключения
- Автоматически закрывает сессию после использования (через `finally`)
- При ошибке делает rollback

#### Реализация:
- Использует паттерн dependency injection
- Обработка ошибок подключения
- Логирование всех операций с БД

### `backend/app/models.py`

#### Логика работы:
**Назначение**: Определение структуры данных в БД через SQLAlchemy ORM.

#### Основные модели:

**1. Enum `RepeatType`**:
```python
class RepeatType(enum.Enum):
    NONE = "NONE"
    DAILY = "DAILY"
    WEEKLY = "WEEKLY"
    MONTHLY = "MONTHLY"
    CUSTOM = "CUSTOM"
```
- Определяет типы повторения задач
- Используется в модели Task

**2. Модель `Task` (таблица `tasks`)**:

**Основные поля**:
- `id` - первичный ключ
- `user_id` - ID пользователя Telegram (индекс для быстрого поиска)
- `title` - название задачи (обязательное, до 255 символов)
- `description` - описание задачи (опциональное, до 1000 символов)
- `created_at` - дата создания (автоматически устанавливается через `func.now()`)

**Поля выполнения**:
- `completed` - статус выполнения (boolean, по умолчанию False)
- `last_completed_date` - дата последнего выполнения (для расчета стриков)
- `streak` - количество последовательных выполнений

**Поля повторения**:
- `repeat_type` - тип повторения (Enum RepeatType, по умолчанию NONE)
- `repeat_interval` - интервал повторения (например, каждые 2 дня)
- `next_due_date` - следующая дата выполнения
- `end_date` - дата окончания повторения

**Поля категоризации**:
- `category` - категория задачи (sport, study, work, personal)
- `frequency` - частота выполнения (daily, weekly, monthly)

**Поля архивирования**:
- `deleted` - флаг мягкого удаления (по умолчанию False)
- `deleted_at` - дата удаления

**Связи**:
- `subtasks` - relationship с моделью Subtask (cascade delete)

**3. Модель `Subtask` (таблица `subtasks`)**:

**Поля**:
- `id` - первичный ключ
- `task_id` - внешний ключ на Task (с CASCADE DELETE)
- `title` - название подзадачи (обязательное)
- `created_at` - дата создания
- `completed` - статус выполнения

**Связи**:
- `task` - обратная связь с Task

**4. Модель `Note` (таблица `notes`)**:

**Поля**:
- `id` - первичный ключ
- `user_id` - ID пользователя Telegram
- `content` - текст заметки (до 1000 символов)
- `date` - дата заметки в формате YYYY-MM-DD
- `mood` - настроение (опциональное, строка с эмодзи)
- `created_at` - дата создания записи

#### Реализация:
- Все модели наследуются от `Base` (declarative_base)
- Используются индексы для оптимизации запросов
- Timezone-aware даты для корректной работы с часовыми поясами
- Cascade delete для автоматического удаления подзадач при удалении задачи

### `backend/app/schemas.py`

#### Логика работы:
**Назначение**: Pydantic схемы для валидации данных при запросах и ответах API.

#### Основные схемы:

**1. `TaskCreate`** - схема для создания/обновления задачи:
```python
class TaskCreate(BaseModel):
    title: str
    description: Optional[str] = None
    repeat_type: RepeatType = RepeatType.NONE
    repeat_interval: int = 1
    next_due_date: Optional[datetime] = None
    end_date: Optional[datetime] = None
    category: str = 'personal'
    frequency: str = 'daily'
```
- Используется в POST `/task` и PUT `/task/{task_id}`
- Автоматически валидирует типы данных
- Поля имеют значения по умолчанию

**2. `TaskOut`** - схема для ответа API с задачей:
```python
class TaskOut(BaseModel):
    id: int
    user_id: int
    title: str
    description: Optional[str]
    # ... все поля задачи
    subtasks: List[SubtaskOut] = []
    
    model_config = ConfigDict(from_attributes=True)
```
- `from_attributes=True` позволяет автоматически конвертировать SQLAlchemy модели в Pydantic схемы
- Включает список подзадач

**3. `SubtaskCreate`** - схема для создания подзадачи:
```python
class SubtaskCreate(BaseModel):
    task_id: int
    title: str
```

**4. `SubtaskUpdate`** - схема для обновления подзадачи:
```python
class SubtaskUpdate(BaseModel):
    title: str
```

**5. `SubtaskOut`** - схема для ответа с подзадачей

**6. `NoteCreate`** - схема для создания записи:
```python
class NoteCreate(BaseModel):
    content: str
    date: str  # YYYY-MM-DD
    mood: Optional[str] = None
```

**7. `NoteOut`** - схема для ответа с записью

#### Реализация:
- Автоматическая валидация типов данных
- Преобразование между SQLAlchemy моделями и Pydantic схемами
- Использование Optional для опциональных полей

### `backend/app/crud.py`

#### Логика работы:
**Назначение**: Содержит всю бизнес-логику работы с данными - CRUD операции и сложные вычисления.

#### Основные функции:

**1. `create_task()`** - создание задачи:
- Принимает все параметры задачи
- Преобразует пустую строку description в None
- Создает Task объект и сохраняет в БД
- Возвращает созданную задачу

**2. `get_task()`** - получение задачи:
- Использует SQLAlchemy select для безопасного запроса
- Фильтрует по `task_id` и `user_id` (безопасность)
- Возвращает None если задача не найдена

**3. `update_task()`** - обновление задачи:
- Получает задачу через `get_task()`
- Обновляет все поля
- Сохраняет изменения в БД

**4. `delete_task()`** - мягкое удаление:
- НЕ удаляет запись из БД
- Устанавливает `deleted = True`
- Записывает `deleted_at = datetime.now()`
- Удаленные задачи остаются в архиве для прошлых дат

**5. `list_tasks_with_subtasks()`** - получение списка задач с автоматическим обновлением:

**Логика работы** (самая сложная функция):

**Шаг 1: Подготовка дат**:
- Получает текущую дату и выбранную дату
- Нормализует все даты (устанавливает время в 00:00:00)
- Убеждается что все даты timezone-aware (UTC)

**Шаг 2: Загрузка задач**:
- Загружает все задачи пользователя одним запросом с eager loading подзадач (`joinedload`)
- Для текущей/будущей даты исключает удаленные задачи
- Для прошлых дат включает удаленные задачи (архив)

**Шаг 3: Автоматическое обновление статусов**:
- **Ежедневные задачи (daily)**:
  - Если прошло больше дня с последнего выполнения - сбрасывает `completed = False`
  - Выполненные ежедневные задачи всегда сбрасываются на новый день
  - Обновляет стрик если был пропуск
  
- **Еженедельные задачи (weekly)**:
  - Если задача не выполнена - видна каждый день текущей недели
  - Выполненные задачи остаются выполненными до начала новой недели
  - Проверяет начало новой недели по `last_completed_date`
  
- **Месячные задачи (monthly)**:
  - Аналогично еженедельным, но проверяет начало нового месяца

**Шаг 4: Фильтрация по выбранной дате**:
- Определяет статус выполнения для выбранной даты:
  - **Daily**: проверяет совпадение дня выполнения с выбранным днем
  - **Weekly**: проверяет принадлежность выбранного дня к неделе выполнения
  - **Monthly**: проверяет принадлежность выбранного дня к месяцу выполнения

**Шаг 5: Фильтрация по типу частоты**:
- **Daily**: показывает для всех дней после создания
- **Weekly**: показывает только если выбранный день в той же неделе что и задача
- **Monthly**: показывает только если выбранный день в том же месяце что и задача

**6. `set_task_completed()`** - установка статуса выполнения:
- Устанавливает `completed` статус
- При выполнении:
  - Записывает `last_completed_date = текущее время`
  - Вычисляет новый стрик через `calculate_streak_on_complete()`
  - Обновляет `next_due_date` если задача повторяющаяся
- При отмене выполнения:
  - Сбрасывает `last_completed_date = None`
  - Сбрасывает `streak = 0`

**7. `calculate_streak_on_complete()`** - вычисление стрика при выполнении:

**Логика для daily**:
- Если первое выполнение → стрик = 1
- Если выполнение в тот же день → стрик не меняется
- Если выполнение было вчера → стрик увеличивается на 1
- Если пропущен день или больше → стрик сбрасывается до 1

**Логика для weekly**:
- Проверяет последовательность недель
- Если выполнение в ту же неделю → стрик не меняется
- Если выполнение было на прошлой неделе → стрик увеличивается
- Если пропущена неделя → стрик сбрасывается

**Логика для monthly**:
- Аналогично weekly, но проверяет месяцы

**8. `reset_streak_if_missed()`** - проверка и сброс стрика при пропуске:
- Вызывается автоматически при загрузке задач
- Проверяет пропуск периода выполнения
- Сбрасывает стрик если был пропуск

**9. `get_stats()`** - получение статистики:
- Подсчитывает выполненные, в процессе и предстоящие задачи
- Фильтрует по периоду (day, week, month, all)
- Оптимизировано для работы с большим количеством задач (использует COUNT вместо загрузки всех записей)

**10. Функции для подзадач**:
- `create_subtask()` - создание подзадачи
- `delete_subtask()` - удаление подзадачи (с проверкой принадлежности пользователю)
- `set_subtask_completed()` - переключение статуса подзадачи
- `update_subtask()` - обновление подзадачи

**11. Функции для заметок**:
- `create_note()` - создание заметки
- `get_notes_by_date()` - получение заметок за дату
- `delete_note()` - удаление заметки

#### Реализация:
- Все функции работают с сессией БД через dependency injection
- Автоматический commit изменений
- Обработка timezone-aware дат для корректной работы
- Оптимизация запросов через eager loading и COUNT

### `backend/app/habits_stats.py`

#### Логика работы:
**Назначение**: Получение статистики по категориям привычек.

#### Функция `get_habits_stats()`:

**Логика**:
1. Загружает все не удаленные задачи пользователя
2. Группирует задачи по категориям
3. Для каждой категории находит максимальный стрик среди всех задач
4. Возвращает список категорий отсортированный по максимальному стрику

**Результат**:
```python
[
    {
        'category': 'sport',
        'max_streak': 15,
        'has_tasks': True
    },
    ...
]
```

#### Реализация:
- Использует простой SQL запрос без сложных JOIN

### `backend/app/telegram_auth.py`

#### Логика работы:
**Назначение**: Валидация данных аутентификации из Telegram WebApp.

#### Как работает Telegram WebApp аутентификация:

1. Telegram клиент отправляет `initData` в заголовке `X-Telegram-Init-Data`
2. Данные содержат информацию о пользователе и подпись (hash)
3. Backend проверяет подпись используя секретный ключ (токен бота)

#### Основные компоненты:

**1. `generate_secret_key()`**:
```python
def generate_secret_key(token: str) -> bytes:
    base = "WebAppData".encode("utf-8")
    token_enc = token.encode("utf-8")
    return hmac.digest(base, token_enc, hashlib.sha256)
```
- Генерирует секретный ключ из токена бота
- Использует алгоритм, описанный в документации Telegram

**2. Класс `TelegramAuthenticator`**:

**Методы**:
- `__parse_init_data()` - парсит строку initData в словарь
- `__parse_json()` - парсит JSON данные пользователя
- `_validate()` - проверяет подпись через HMAC-SHA256
- `_check_expiry()` - проверяет срок действия данных (по умолчанию 1 день)
- `validate()` - главный метод валидации

**Процесс валидации**:
1. Парсит initData в словарь
2. Извлекает hash из данных
3. Создает строку для проверки (все поля кроме hash, отсортированные по ключу)
4. Вычисляет HMAC-SHA256 от строки с секретным ключом
5. Сравнивает вычисленный hash с переданным
6. Проверяет срок действия данных
7. Парсит данные пользователя в структурированный объект

**3. Функция `parse_and_validate_init_data()`**:
- Получает BOT_TOKEN из переменных окружения
- Создает TelegramAuthenticator с секретным ключом
- Вызывает validate() с таймаутом 1 день
- Извлекает user_id из объекта пользователя
- Возвращает словарь с данными пользователя или None при ошибке

#### Обработка ошибок:
- `InvalidInitDataError` - неверные данные или подпись
- `ExpiredInitDataError` - данные истекли
- Все ошибки логируются

#### Реализация:
- Безопасное сравнение hash через `hmac.compare_digest()` (защита от timing attacks)
- Поддержка разных форматов данных пользователя (dict, model_dump, __dict__)
- Fallback для минимального payload (только user_id)

## Логика работы системы

### Жизненный цикл задачи

**1. Создание задачи**:
- Пользователь заполняет форму
- Frontend отправляет POST `/task`
- Backend создает запись в БД с `completed = False`
- Задача появляется в списке

**2. Автоматическое обновление статуса**:
- При загрузке списка задач (`list_tasks_with_subtasks`)
- Система проверяет частоту задачи:
  - **Daily**: Если прошло больше дня - сбрасывает `completed`
  - **Weekly**: Если началась новая неделя - сбрасывает `completed`
  - **Monthly**: Если начался новый месяц - сбрасывает `completed`

**3. Выполнение задачи**:
- Пользователь кликает чекбокс
- Frontend отправляет POST `/task/{id}/complete`
- Backend:
  - Устанавливает `completed = True`
  - Записывает `last_completed_date = now()`
  - Вычисляет новый стрик
  - Обновляет `next_due_date` если задача повторяющаяся

**4. Стрик (последовательные выполнения)**:
- При выполнении проверяется:
  - Если выполнение в предыдущем периоде - стрик увеличивается
  - Если был пропуск - стрик сбрасывается до 1
- При загрузке задач автоматически проверяется пропуск периода

**5. Мягкое удаление**:
- При удалении задача не удаляется из БД
- Устанавливается `deleted = True`
- Для текущей/будущей даты удаленные задачи не показываются
- Для прошлых дат удаленные задачи показываются (архив)

### Логика подзадач

**1. Создание подзадачи**:
- Пользователь создает подзадачу для задачи
- Подзадача сохраняется с `task_id` родительской задачи

**2. Автоматическое выполнение задачи**:
- Если все подзадачи выполнены - автоматически отмечается задача
- Если хотя бы одна подзадача не выполнена - задача отменяется

**3. Удаление подзадачи**:
- При удалении проверяется состояние оставшихся подзадач
- Если задача была выполнена, но теперь не все подзадачи выполнены - задача отменяется

### Логика фильтрации по датам

**Ежедневные задачи (daily)**:
- Показываются для всех дней после создания
- Статус выполнения определяется по `last_completed_date`:
  - Если `last_completed_date` совпадает с выбранным днем - задача выполнена

**Еженедельные задачи (weekly)**:
- Показываются только для дней текущей недели задачи
- Если задача выполнена - показывается в неделе выполнения
- Статус определяется по принадлежности выбранного дня к неделе выполнения

**Месячные задачи (monthly)**:
- Аналогично еженедельным, но для месяцев
- Показываются только для дней текущего месяца задачи

### Логика статистики

**Статистика по периодам**:
- **day**: Статистика за сегодня
- **week**: Статистика за текущую неделю
- **month**: Статистика за текущий месяц
- **all**: Статистика за все время

**Категории привычек**:
- Группировка задач по категориям
- Для каждой категории определяется максимальный стрик
- Отсортировано по максимальному стрику

Проект представляет собой полнофункциональное приложение для отслеживания привычек с продуманной архитектурой и детальной реализацией бизнес-логики. Все компоненты работают согласованно, обеспечивая удобный пользовательский опыт и надежную работу с данными.
