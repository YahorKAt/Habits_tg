# Рефакторинг проекта

## Примененные принципы

### KISS (Keep It Simple, Stupid)
- Простые, понятные функции с одной ответственностью
- Минимум абстракций, только необходимые
- Понятные названия переменных и функций

### DRY (Don't Repeat Yourself)
- Вынесены повторяющиеся API вызовы в сервисы
- Общая логика операций с задачами в хуках
- Переиспользуемые UI компоненты

### YAGNI (You Aren't Gonna Need It)
- Удалены неиспользуемые абстракции
- Только необходимый функционал

### SOLID
- **Single Responsibility**: каждый модуль отвечает за одну вещь
- **Open/Closed**: легко расширять через новые сервисы/компоненты
- **Dependency Inversion**: компоненты зависят от абстракций (сервисы), а не от конкретных реализаций

## Разделение слоев

### 1. Слой интеграций (services/)
Отвечает за все взаимодействие с API:
- `taskService.js` - все запросы, связанные с задачами
- `noteService.js` - все запросы, связанные с заметками
- `statisticsService.js` - все запросы, связанные со статистикой

**Принцип**: Один сервис = одна доменная область

### 2. Слой бизнес-логики (hooks/)
Инкапсулирует бизнес-логику и состояние:
- `useTaskOperations.js` - операции с задачами (toggle, delete, etc.)
- `useNoteOperations.js` - операции с заметками

**Принцип**: Хуки управляют состоянием и бизнес-логикой, компоненты только отображают

### 3. Презентационный слой (components/)
Чистые UI компоненты:
- `TaskForm.jsx` - форма создания/редактирования задачи
- `SubtaskForm.jsx` - форма создания/редактирования подзадачи
- `MoodIcon.jsx` - компонент иконки настроения
- `BottomNavigation.jsx` - навигация

**Принцип**: Компоненты получают данные через props, вызывают колбэки

### 4. Слой страниц (pages/)
Композиция компонентов и хуков:
- `TasksPage.jsx` - страница задач
- `StatisticsPage.jsx` - страница статистики
- `JournalPage.jsx` - страница журнала

**Принцип**: Страницы объединяют компоненты и логику

## Преимущества новой структуры

1. **Модульность**: Каждый модуль независим и может быть легко заменен
2. **Тестируемость**: Сервисы и хуки легко тестировать изолированно
3. **Переиспользование**: Компоненты и хуки можно использовать в разных местах
4. **Читаемость**: Код легче понять благодаря четкому разделению ответственности
5. **Масштабируемость**: Легко добавлять новый функционал

## Примеры использования

### Использование сервиса
```javascript
import * as taskService from './services/taskService.js'

const apiClient = createApiClient(initData)
const task = await taskService.createTask(apiClient, {
  title: 'Новая задача',
  description: 'Описание',
  category: 'personal',
  frequency: 'daily'
})
```

### Использование хука
```javascript
import { useTaskOperations } from './hooks/useTaskOperations.js'

const { toggleTask, deleteTask, togglingTasks } = useTaskOperations(apiClient)

// В компоненте
<button 
  onClick={() => toggleTask(task, isPastDate, handleUpdate)}
  disabled={togglingTasks.has(task.id)}
>
  Переключить
</button>
```

## Рекомендации

1. **Не смешивать слои**: Сервисы не должны знать о React, компоненты не должны делать API запросы напрямую
2. **Использовать хуки для состояния**: Вся бизнес-логика в хуках, компоненты только отображают
3. **Маленькие функции**: Каждая функция делает одну вещь
4. **Понятные названия**: `createTask` лучше чем `ct`, `handleSubmit` лучше чем `onClick`
5. **Документация**: JSDoc комментарии для сложных функций
